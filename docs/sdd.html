1. 설계 원칙

  1. 웹을 덮어쓰지 않는다: 모든 업로드는 버전 비교를 통과해야 한다. (NFR-01)
  2. 바꾼 것만 올린다: 변경 판단은 변환 결과가 아니라 파일 해시로 한다. (NFR-02)
  3. 모르는 건 보존한다: 해석할 수 없는 Storage 요소는 원본 XML로 보존한다.
  4. git에 맡긴다: 이력, diff, merge는 직접 구현하지 않고 git을 쓴다.
  5. 페이지 단위로 실패한다: 한 페이지 실패가 전체 작업을 멈추지 않는다.

3. 브랜치 모델

로컬 git 저장소는 두 개의 브랜치를 쓴다.

브랜치내용누가 커밋하나
confluence마지막으로 확인한 웹 상태 그대로. 사람이 직접 수정하지 않는다.wiki-sync만
main사용자의 작업 브랜치. 로컬 수정과 웹 변경이 합쳐진 상태사용자, wiki-sync

웹 변경은 항상 confluence 브랜치에 먼저 커밋되고, main으로 merge된다. 덕분에 3-way merge와 충돌 표시를 git이 처리한다.

4. 처리 흐름

4.1 clone

  1. 스페이스 키로 스페이스 ID와 홈 페이지 ID를 조회한다.
  2. 스페이스의 모든 페이지를 본문 포함으로 페이지네이션하며 받는다. --root가 있으면 그 페이지의 하위 트리만 남긴다.
  3. parentId로 트리를 만들고, 페이지마다 파일 경로를 정한다(DSD 4장 경로 규칙).
  4. 각 페이지를 Markdown으로 변환해 front matter와 함께 저장하고, 인덱스에 id · 경로 · 버전 · 해시를 기록한다.
  5. git init → confluence 브랜치에 첫 커밋 → main 브랜치를 같은 커밋에서 만든다.

4.2 status

  1. 작업 폴더의 모든 .md 파일을 읽고 front matter의 id를 모은다.
  2. 판정 규칙:
    • id가 인덱스에 있고, 본문 해시가 인덱스의 baseHash와 다름 → M (수정)
    • id가 인덱스에 있고, 경로 또는 제목이 다름 → R (이동 · 이름 변경)
    • id가 없음 → A (신규)
    • 인덱스에 있는 id가 어떤 파일에도 없음 → D (삭제)
    • 파일에 git 충돌 표시(<<<<<<<)가 남아 있음 → C (충돌 미해결)
  3. status는 네트워크를 쓰지 않는다. 웹 쪽 변경은 pull · push 때 확인한다.

4.3 pull

  1. 작업 폴더에 커밋되지 않은 변경이 있으면 자동으로 커밋한다(메시지: wiki: 로컬 변경 저장).
  2. 스페이스 페이지 목록을 본문 없이 받아 인덱스 버전과 비교한다. 버전이 높아진 페이지, 새 페이지, 사라진 페이지를 찾는다.
  3. 바뀐 페이지만 본문을 받는다.
  4. confluence 브랜치를 별도 작업 트리(git worktree, .wiki/remote)에서 열어, 변환 결과를 쓰고 커밋한다. 사용자 작업 트리는 건드리지 않는다.
  5. main에서 git merge confluence를 실행한다.
  6. 충돌이 없으면 인덱스의 version · baseHash를 갱신한다. 충돌이 있으면 충돌 파일 목록을 출력하고, 해당 페이지의 인덱스는 웹 버전만 갱신한다(해결 후 push 가능 상태).

4.4 push

  1. status를 계산한다. C가 있으면 해당 페이지는 제외하고 경고한다.
  2. 변경분을 자동 커밋한다(메시지: -m 값 또는 wiki push).
  3. 처리 순서: 신규(A, 부모가 먼저) → 이동 · 이름 변경(R) → 수정(M) → 삭제(D, --allow-delete일 때).
  4. 페이지마다:
    1. 웹의 현재 버전을 조회한다. 인덱스 version과 다르면 충돌로 기록하고 다음 페이지로 간다.
    2. Markdown → Storage로 변환한다.
    3. 버전 +1로 업로드한다. 서버가 409(버전 불일치)를 주면 충돌로 기록한다.
    4. 성공하면 인덱스의 version · baseHash를 갱신하고 즉시 저장한다(중간 실패 대비).
  5. 성공한 페이지의 웹 본문을 다시 받아 confluence 브랜치에 커밋하고 main에 merge한다. 변환 왕복에 차이가 있다면 이 단계에서 드러난다.
  6. 결과 요약(성공 · 충돌 · 실패 수)을 출력하고 종료 코드를 정한다(DID 2.3장).

--dry-run은 4-1 버전 조회까지만 하고 업로드 · 커밋 · 인덱스 갱신을 하지 않는다.

5. 변환 설계

5.1 Storage → Markdown

  • Storage 본문을 ac · ri 네임스페이스 선언이 있는 루트로 감싸 XML 파서(lxml)로 읽는다.
  • 요소별 변환기를 등록하는 방식이다(h1~h6, p, ul/ol/li, table, a, strong/em/code, ac:link, ac:image, ac:structured-macro[name=code]).
  • 등록되지 않은 요소는 원본 XML을 그대로 ```confluence-storage 블록으로 출력한다.
  • 셀 병합(rowspan/colspan)이 있는 표는 HTML 표로 그대로 둔다.
  • 출력은 정규화한다(줄 끝 LF, 마지막 줄바꿈 1개, 목록 들여쓰기 2칸). 같은 입력이면 항상 같은 출력이 나와야 한다.

5.2 Markdown → Storage

  • markdown-it-py(CommonMark + 표 확장)로 파싱하고, 전용 렌더러가 XHTML을 만든다.
  • ```confluence-storage 블록은 내용을 그대로 출력한다. XML로 파싱되지 않으면 해당 페이지 업로드를 중단하고 오류를 보고한다.
  • 상대 경로 .md 링크는 인덱스에서 대상 페이지 제목을 찾아 ac:link로 바꾼다. 대상이 없으면 일반 링크로 두고 경고한다.
  • _attachments/<id>/ 아래 이미지는 ac:image + ri:attachment로 바꾼다.

5.3 왕복 보장

테스트 기준: 샘플 Storage S에 대해 md1 = toMd(S), md2 = toMd(toStorage(md1))일 때 md1 == md2여야 한다. Storage끼리는 서식 공백이 달라질 수 있으므로 Markdown 기준으로 비교한다.

6. 오류 처리

오류처리
401 · 403 (인증 · 권한)401은 전체 중단하고 wiki login 안내. 403은 해당 페이지만 "권한 없음"으로 건너뜀
404 (페이지 없음)웹에서 삭제된 것으로 판단. push는 건너뛰고 경고, pull은 로컬 파일 유지 후 안내
409 (버전 불일치)충돌로 기록
429 · 5xxRetry-After 헤더가 있으면 그만큼, 없으면 1 · 2 · 4 · 8 · 16초 지수 백오프로 최대 5회 재시도
네트워크 단절재시도 후 실패하면 중단. 이미 성공한 페이지는 인덱스에 반영된 상태 유지
변환 실패해당 페이지만 실패 처리, 원인 요소 위치를 출력
git 명령 실패명령과 stderr를 출력하고 중단

7. 동시성과 성능

  • 페이지 본문 조회 · 업로드는 동시 4개로 제한한다(설정 가능, 최대 8).
  • 목록 조회는 한 번에 최대 250개씩 받는다.
  • 인덱스 저장은 임시 파일에 쓴 뒤 교체하는 방식으로 원자적으로 한다.
  • 같은 작업 폴더에서 두 명령이 동시에 돌지 않도록 .wiki/lock 파일로 잠근다.

8. 로깅

  • 로그 위치: .wiki/logs/wiki-YYYYMMDD.log (git 제외)
  • 기록: 명령, 호출한 API 경로 · 상태 코드 · 소요 시간, 페이지별 결과
  • 기록하지 않음: 토큰, 인증 헤더, 페이지 본문
  • --verbose는 같은 내용을 화면에도 출력한다.
