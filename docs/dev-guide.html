3. 개발 환경 구성

  1. Python 3.12와 git 2.30 이상을 설치한다.
  2. 저장소를 받고 가상환경을 만든다. 
    git clone <사내 저장소 주소>/wiki-sync.git
cd wiki-sync
uv venv
uv pip install -e ".[dev]"
  3. 동작을 확인한다. 
    wiki --version
pytest
  4. 테스트용 Confluence 스페이스를 하나 만든다(개인 스페이스 권장). 실제 업무 스페이스로 개발하지 않는다.
  5. API 토큰은 Atlassian 계정 설정의 보안 메뉴에서 발급하고, wiki login으로 등록한다. 토큰을 코드나 .env에 넣지 않는다.

4. 코딩 규칙

  • 포맷 · 린트는 ruff, 타입은 mypy strict를 통과해야 한다.
  • 모듈 간 의존 방향: cli → sync → (client, convert, index, gitops). 하위 모듈은 상위 모듈을 import하지 않는다.
  • HTTP 오류는 client.py에서 도메인 예외(AuthError, ConflictError, NotFoundError, RateLimitError)로 바꾼다. 상위 모듈은 HTTP 상태 코드를 직접 다루지 않는다.
  • 사용자에게 보이는 메시지는 한국어로, 다음 행동을 함께 안내한다. 예: "로그인이 만료되었습니다. wiki login을 실행하세요."
  • 로그에 토큰 · 인증 헤더 · 페이지 본문을 남기지 않는다.
  • 파일 쓰기는 항상 UTF-8, 줄 끝 LF로 한다.

5. 테스트

명령내용
pytest tests/unit단위 테스트
pytest tests/integrationHTTP 모킹 통합 테스트 (네트워크 불필요)
pytest -m e2e실제 테스트 스페이스 대상. 환경 변수 WIKISYNC_E2E_SPACE 필요
pytest --update-golden변환기 기대 결과 갱신 (diff를 꼭 검토)

변환기 샘플 추가 방법

  1. 문제가 된 페이지의 Storage 본문을 받아 tests/fixtures/storage/<이름>.xml로 저장한다. 사내 정보는 지운다.
  2. 기대 Markdown을 tests/fixtures/golden/<이름>.md로 만든다.
  3. 변환 테스트와 왕복 테스트가 모두 통과하도록 변환기를 고친다.

6. 브랜치와 리뷰

  • 기본 브랜치는 main. 작업은 feat/…, fix/… 브랜치에서 하고 PR로 합친다.
  • PR 조건: 테스트 · ruff · mypy 통과, 리뷰어 1명 승인
  • 변환기 변경 PR에는 바뀐 golden 파일의 diff를 설명에 요약한다.
  • 커밋 메시지는 무엇을 왜 바꿨는지 한 줄로 쓴다. 예: push: 409 응답을 충돌로 처리

7. 빌드와 배포

  1. 버전은 pyproject.toml의 version을 올린다(유의적 버전: 0.x 동안은 형식 변경 시 minor 증가).
  2. Windows 실행 파일 빌드: 
    pyinstaller --onefile --name wiki src/wikisync/__main__.py
  3. 사내 배포 위치에 wiki.exe와 변경 내역을 올린다. 사용자는 PATH에 있는 폴더에 복사하면 된다.
  4. 개발자는 uv tool install 또는 pipx install로 설치해도 된다.

9. 자주 겪는 문제

clone 후 바로 status를 했는데 파일이 수정됨(M)으로 나와요

git의 core.autocrlf 설정으로 줄 끝이 바뀌었을 가능성이 크다. 해시는 LF로 정규화해 계산하므로 정상이라면 나오지 않아야 한다. 해시 계산 코드에서 정규화가 빠지지 않았는지 확인한다.

업로드 시 400 오류가 나요

대부분 Storage XML 형식 오류다. --verbose로 응답 메시지를 보고, 해당 페이지를 변환기 샘플로 추가해 재현한다.

경로가 너무 길다는 오류가 나요 (Windows)

maxFileNameLength를 줄이거나 작업 폴더를 C:\wiki처럼 짧은 경로에 둔다.
